---
title: "IntelliSense"
description: "Use project-aware suggestions for Statamic handles, tags, fields, attributes, modifiers, and examples."
---

The extension provides IntelliSense that understands both Statamic conventions and the project currently open in VS Code.

Suggestions are not just generic snippets. They can come from collections, taxonomies, globals, navigation files, blueprints, fieldsets, partial files, open Antlers blocks, and surrounding HTML attributes.

## Core Statamic tag suggestions

At the start of an Antlers tag, the extension suggests common Statamic tags with rich documentation and examples.

Examples include:

- `if`
- `unless`
- `collection`
- `nav`
- `partial`
- `taxonomy`
- `terms`
- `entries`
- `global`

Documentation can include:

- Summary text
- Common variables
- Common parameters
- Fenced Antlers examples
- Official Statamic documentation links

## Open suggestions on demand

Press `Ctrl+.` on Windows/Linux or `Command+.` on macOS in an Antlers file to open VS Code's normal suggestion widget.

Use this when quick suggestions are hidden, dismissed, or you want to ask for project-aware Antlers completions at the current cursor position.
## Insert the shown example

When the IntelliSense details panel shows a code example, press `Ctrl+Enter` on Windows/Linux or `Command+Enter` on macOS.

The extension accepts the currently selected suggestion and expands that same suggestion's first documented code example.

For example, if the selected suggestion is `featured_image`, the example can expand into:

```html
{{ featured_image }}
  <img src="{{ url }}" alt="{{ alt ?? title }}">
{{ /featured_image }}
```

If the selected suggestion is `title`, the inserted example is based on the `title` suggestion instead.

When the cursor is inside an unfinished Antlers tag such as `{{ fea }}`, the whole tag is replaced with the example. This avoids nested braces and keeps the pasted code clean.

## Collection suggestions

Collection handle suggestions work in shorthand tags:

```html
{{ collection:blog }}
  {{ title }}
{{ /collection:blog }}
```

They also work inside `from` attributes:

```html
{{ collection from="blog" limit="3" }}
  {{ title }}
{{ /collection }}
```

Collection suggestions can show:

- Shorthand usage
- `from` usage
- Indexed entry counts
- Recent entry titles when content files are available

When you complete a `from="..."` value, the cursor moves outside the closing quote so you can keep typing attributes.

## Current collection helpers

The `collection:next` and `collection:previous` completions are context-aware. Their examples use the current entry collection instead of hard-coding a collection handle.

```html
{{ collection:next in="{ collection }" as="next_entries" }}
  {{ if no_results }}
    <span class="opacity-50 pointer-events-none">Next</span>
  {{ /if }}

  {{ next_entries }}
    <a href="{{ url }}">Next: {{ title }}</a>
  {{ /next_entries }}
{{ /collection:next }}
```

Inside the `in=""` value, IntelliSense suggests every indexed collection plus `{ collection }` for the current entry collection.

## Collection search generator

Type `{{ search:generate }}` in an Antlers file to create a reusable collection search partial.

When you accept the completion, the extension inserts a partial call like this:

```html
{{ partial:search.search
  search_collection="projects"
  search_result_partial="search.result"
  search_no_results_text="No results."
/ }}
```

It also creates these files:

<Tree>
  <Tree.Folder defaultOpen name="resources">
    <Tree.Folder defaultOpen name="views">
      <Tree.Folder defaultOpen name="partials">
        <Tree.Folder defaultOpen name="search">
          <Tree.File name="search.antlers.html" />
          <Tree.File name="_result.antlers.html" />
        </Tree.Folder>
      </Tree.Folder>
    </Tree.Folder>
  </Tree.Folder>
</Tree>

Use `search_collection` to choose the collection:

```html
{{ partial:search.search
  search_collection="projects"
  search_result_partial="search.result"
  search_no_results_text="No results."
/ }}
```

For multiple collections, separate handles with a pipe and no spaces:

```html
{{ partial:search.search
  search_collection="pages|projects"
  search_result_partial="search.result"
  search_no_results_text="No results."
/ }}
```

Edit `resources/views/partials/search/_result.antlers.html` to style each result. It renders inside the collection entry context, so entry variables such as `{{ url }}`, `{{ title }}`, and `{{ content }}` point at the actual result.

```html
<a href="{{ url }}">
  <h2>{{ title }}</h2>
  <p>{{ content | strip_tags | truncate:180 }}</p>
</a>
```

The generated search partial uses a `q` query parameter, fetches the current page, and swaps the `#results` element without a full page reload.

## Manual form partial generator

After a form handle, type `:manual` to create a blueprint-driven manual form partial. Use Statamic's singular `form` tag.

```html
{{ form:contact:manual }}
```

The completion inserts this at the cursor:

```html
{{ partial:forms.contact }}
```

It also creates the generated form partial and the missing fieldtype partials:

<Tree>
  <Tree.Folder defaultOpen name="resources">
    <Tree.Folder defaultOpen name="views">
      <Tree.Folder defaultOpen name="partials">
        <Tree.Folder defaultOpen name="forms">
          <Tree.File name="_contact.antlers.html" />
          <Tree.Folder defaultOpen name="fields">
            <Tree.Folder defaultOpen name="contact">
              <Tree.File name="_style.antlers.html" />
              <Tree.File name="_required.antlers.html" />
              <Tree.File name="_options.antlers.html" />
              <Tree.File name="_input_type.antlers.html" />
              <Tree.File name="_autocomplete.antlers.html" />
            </Tree.Folder>
            <Tree.File name="_text.antlers.html" />
            <Tree.File name="_textarea.antlers.html" />
            <Tree.File name="_select.antlers.html" />
            <Tree.File name="_checkboxes.antlers.html" />
          </Tree.Folder>
        </Tree.Folder>
      </Tree.Folder>
    </Tree.Folder>
  </Tree.Folder>
</Tree>

The generated form partial uses `data-statamic-ajax-*` attributes and an inline guarded `fetch` handler. It does not require `resources/js/forms/ajax.js` in the Vite manifest, and CSS class obfuscation will not break the JavaScript.

Running `{{ form:contact:manual }}` again preserves custom form markup and custom field partial markup. It only repairs known generated helpers and migrates older generated form partials away from the old Vite-loaded AJAX file.

## Navigation, taxonomy, global, and partial handles

The extension suggests:

- Navigation handles after `{{ nav: }}`
- Taxonomy handles after `{{ taxonomy: }}` and inside `from=""`
- Global set handles at the start of Antlers tags
- Partial handles after `{{ partial: }}` and inside `src=""`
- Partial handles in `partial:if_exists` and `partial:exists`

Partial suggestions hide leading underscores from filenames while still resolving the correct file.

A file named `_hero_card.antlers.html` is suggested as `hero_card`.

Nested folders are suggested one segment at a time. A partial at `resources/views/partials/sets/pages/_hero_section.antlers.html` can be discovered through `sets`, then `sets.pages`, then `sets.pages.hero_section`.

## Partial documentation

Partial handle suggestions read the matching partial file and show:

- Inferred props
- Default slots
- Named slots
- A focused usage example

The prop inference ignores common Statamic variables such as `title`, `url`, `slug`, and `permalink` so loop partials do not get noisy fake props.

- `handle`

- `src`
- `when`
- `unless`

## Sort value suggestions

Inside `sort=""`, collections suggest built-in fields and top-level blueprint fields when the collection handle is known.

```html
{{ collection from="articles" sort="date:desc" }}
  {{ title }}
{{ /collection }}
```

After a value like `date:`, the extension narrows to `asc` and `desc` and documents what the direction means for the current field.

## Modifiers

Modifier suggestions work after pipes:

```html
{{ title | }}
```

Suggestions are ranked by inferred field type.

Text fields prioritize text modifiers. Date fields prioritize date modifiers. Assets prioritize image and file modifiers. Arrays prioritize collection-like modifiers.

Documentation examples use the value being piped, so examples stay close to the code you are writing.

## Conditions and operators

Inside condition tags, the extension ranks boolean-like fields first and suggests comparison operators after completed condition values.

```html
{{ if featured }}
  ...
{{ /if }}
```

```html
{{ if title contains "Research" }}
  ...
{{ /if }}
```

Condition operator suggestions show full in-context examples for `==`, `!=`, `>`, `>=`, `<`, `<=`, `contains`, `starts_with`, `ends_with`, `is empty`, and related patterns.

Collection condition operators are also suggested after field prefixes like `title:` or `taxonomy:tags:`.

## HTML attribute context

Suggestions change based on the HTML attribute around the cursor.

In URL attributes such as `href` and `src`, the extension prioritizes:

- `url`
- `permalink`
- `uri`
- URL fields
- asset fields

In text attributes such as `alt` and `aria-label`, it prioritizes text-like values.

In `id`-style attributes, it prioritizes identifiers like `id`, `slug`, and `handle`.

In `class` attributes, it prioritizes boolean variables that are useful for conditional classes.

Duplicate suggestions from overlapping nav variables, form variables, and blueprint fields are collapsed so the highest-ranked match appears once.

## Blueprint-generated form partials

Form handle completions read `resources/forms/*.yaml` and the form blueprint referenced by that form. When fields are indexed, the completion documentation lists each field with its type, required state, and instructions.

After a form handle, type a second colon to use the `manual` starter:

```html
{{ form:contact_us:manual }}
```

Accepting it inserts only a partial reference at the cursor:

```html
{{ partial:forms.contact_us }}
```

The extension then creates the implementation files:

```txt
resources/views/partials/forms/_contact_us.antlers.html
resources/views/partials/forms/fields/_text.antlers.html
resources/views/partials/forms/fields/_textarea.antlers.html
resources/views/partials/forms/fields/contact_us/_style.antlers.html
resources/views/partials/forms/fields/contact_us/_required.antlers.html
```

The generated form partial renders runtime fields by type and includes a guarded inline AJAX handler:

```html
{{ form:create in="contact_us" data-statamic-ajax-form="true" data-statamic-ajax-success-message="Thanks, your message has been sent." }}
  <div data-statamic-ajax-success {{ unless success }}hidden{{ /unless }}>
    <p role="status">{{ success ?? 'Thanks, your message has been sent.' }}</p>
  </div>

  <div data-statamic-ajax-errors role="alert" {{ unless errors }}hidden{{ /unless }}>
    {{ if errors }}
      {{ errors }}
        <p>{{ value }}</p>
      {{ /errors }}
    {{ /if }}
  </div>

  <div class="form-fields flex w-full flex-wrap gap-4">
    {{ fields }}
      {{ partial:forms.fields.{type} form_handle="contact_us" }}
    {{ /fields }}
  </div>

  <button data-statamic-ajax-submit type="submit">Submit</button>
{{ /form:create }}

<script>
(() => {
  if (window.__statamicAjaxFormsInitialized) return
  window.__statamicAjaxFormsInitialized = true

  document.addEventListener("submit", async (event) => {
    const form = event.target.closest("[data-statamic-ajax-form]")
    if (!form) return

    event.preventDefault()
    ...
  })
})()
</script>
```

Generated field partials are shared by field type. For example, `name` and `e_mail` both use `_text.antlers.html`, while `message` uses `_textarea.antlers.html`.

Form-specific helper partials keep blueprint settings available during Statamic's runtime `{{ fields }}` loop:

- `_style.antlers.html` maps each field handle to Tailwind width classes such as `basis-[calc(50%-1rem)]`.
- `_required.antlers.html` renders the required `*` marker for required blueprint fields.

These helper partials are regenerated from the current form blueprint when `:manual` runs, and they refresh again when Statamic or VS Code saves files under `resources/forms/` or `resources/blueprints/forms/`.

Fieldtype partials and generated form partials are created only when missing, so custom Tailwind classes or edits are preserved on later `:manual` generations. Existing generated form partials migrate away from the old `{{ vite src="resources/js/forms/ajax.js" }}` line without overwriting custom form markup. Existing generated fieldtype partials only receive narrow migrations: slash paths to dot notation, old important modifier order to Tailwind suffix order, old inline width styles to class helpers, and `flex flex-col` wrappers so labels sit above controls.

## AJAX form behavior

Generated manual form partials inline the vanilla JavaScript handler in the partial.

The handler:

- intercepts submit events on `[data-statamic-ajax-form]`
- sends `FormData`, including Statamic's hidden `_token` and `_params` values
- sends `Accept: application/json`
- sends `X-Requested-With: XMLHttpRequest`
- updates `[data-statamic-ajax-success]` and `[data-statamic-ajax-errors]` in place
- disables the submit button while the request is running
- resets the form on success

Because the handler uses only `data-statamic-ajax-*` selectors, CSS obfuscators can safely rename classes without breaking form behavior. Because it is inline, it does not require `resources/js/forms/ajax.js` to exist in the Vite manifest.

## Form field condition suggestions

Inside a manual form condition like this:

```html
{{ if handle == "..." }}
```

the extension suggests field handles from the current form blueprint.
